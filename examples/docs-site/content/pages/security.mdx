  Graft assumes the operator is an autonomous agent. The safety story is
  structural, not a promise.

  Approvals, Postgres role separation, audit receipts, git-authoritative
  content. Why it is safe to let an agent run your CMS.
faqs:
  - question: Can an agent delete my content?
    answer: >-
      Deletes are destructive functions, so the first call never executes — it
      files a one-shot, input-bound approval and returns 403 with its id. Only
      after you run graft approve does the retry succeed, and the deletion is
      still a commit in your history.
  - question: What stops the agent approving itself?
    answer: >-
      Postgres role separation. The runtime credential can request and consume
      approvals only through a SECURITY DEFINER function; flipping pending to
      approved is an operator-role UPDATE stamped server-side with decided_role.
      Even raw SQL with the runtime credential cannot self-approve.
  - question: What happens when a token leaks?
    answer: >-
      Tokens are verified against your OIDC issuer, carry only the scopes you
      granted, and expire on the issuer's schedule. Everything the token did is
      in the audit log. Revocation is at your issuer. A stolen runtime
      credential can still rewrite or hide content_index rows — the approval
      gate is the exception, not a general database lock.
