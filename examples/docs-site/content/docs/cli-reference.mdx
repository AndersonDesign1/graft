<p className="kicker">Every graft command, grouped by when you use it.</p>

Look up a command here. Run `graft --help` for the list of commands in your
terminal, or `graft <command> --help` for one command's usage and flags.
`graft migrate` and `graft merge` only report what they would change until you
pass `--apply`.

## Set up and write content

| Command | What it does |
| --- | --- |
| `graft create [dir]` | Make a new site: a template, a database, Studio, and a Next.js app, installed and with example content. `npm create graft` runs it. Asks three questions, or takes `--template` (blog, docs, shop, portfolio, blank), `--edit` (online, code), `--database` (new, none, or a Postgres URL), `--framework` (next, none), `--yes` and `--no-install`. See [Set up a site for someone](/docs/start). |
| `graft init [dir]` | Create a Graft project: `graft.config.ts`, `content/`, sample content, and `llms.txt`. Add `--postgres` for the Postgres engine. |
| `graft doctor` | Check the setup (the database and its version, the schema, content, the index, Studio sign-in) and print the one thing to do next. `--json` for the checklist as data. Exits 1 when something is missing. |
| `graft compile` | Check every content file against the schema and build the index, once |
| `graft dev` | Watch `content/` and `graft.config.ts`, and recompile on every change. When content is in the database, it compiles once and watches only `graft.config.ts`. |
| `graft asset put <file> [key]` | Upload a file to your bucket and print the frontmatter that points to it. Refuses a key that already holds a file. |
| `graft add [item]` | Copy a ready-made [primitive](/docs/owned-primitives) into `graft/`. With no item, list them. |

### Print what a compile changed

`graft compile --json` prints one JSON object on stdout and nothing else. The
summary line goes to stderr. It works on both engines.

```json
{
  "branch": "main",
  "gitSha": "b8eb719a468be404bae9adca4fbea4d90c642411",
  "changes": {
    "added": ["posts/launch"],
    "changed": ["pages/home"],
    "removed": [],
    "unchanged": 42
  }
}
```

The real output is one line. `added`, `changed`, and `removed` are lists of
`collection/slug` ids, and `unchanged` is a count.
`gitSha` is `null` when the content is not in a git repository.

On the static engine, a content change ships with a new deploy, so there is
nothing to refresh. On the Postgres engine, writes from agents, Studio,
`graft merge` and `graft migrate` call your app's revalidate route when
`GRAFT_REVALIDATE_URL` and `GRAFT_WEBHOOK_SECRET` are both set. With the URL
alone, these commands refuse to start. `graft compile` does not, because a deploy
compiles before the new version is live. Send its output to the route yourself
so the app refreshes only the pages that changed. A shell does not read `.env`,
so export `GRAFT_WEBHOOK_SECRET` in the script's environment first:

```sh
graft compile --json > changes.json || exit 1
curl --fail -X POST https://example.com/api/revalidate \
  -H "Authorization: Bearer $GRAFT_WEBHOOK_SECRET" \
  -H "content-type: application/json" \
  --data-binary @changes.json
```

See [Refresh pages when content changes](/docs/next#refresh-pages-when-content-changes)
for the route.

## Run Graft

| Command | What it does |
| --- | --- |
| `graft mcp` | Serve your project to an agent on this machine, over stdio |
| `graft serve [--port 3903]` | Run Graft's HTTP endpoints: functions, MCP, the Content API, and `/healthz`. Add `--studio` to include Studio. |
| `graft studio` | Open Studio on this machine, at port 4983 |
| `graft studio invite <email>` | Print a sign-in link for a hosted Studio. `--role` (viewer, contributor, editor, admin), `--name`, `--days`, `--url`. Needs `GRAFT_STUDIO_SECRET`, and Studio's public address from `--url` or `GRAFT_STUDIO_URL`: https, or plain http on `localhost`, `127.0.0.1` or `[::1]` |
| `graft studio setup-code` | Print the code a hosted Studio asks for before it creates its owner account. It comes from `GRAFT_STUDIO_SECRET`, so run it with the site's settings |

## Manage the database (Postgres engine)

| Command | What it does |
| --- | --- |
| `graft db migrate` | Create or update the tables Graft needs. Safe to run again. |
| `graft db claim` | Keep the free database `graft create --database new` made, which is deleted after 72 hours unless claimed. Prints the claim link, waits, then saves the new connection string to `.env` (claiming changes the password). `--url` gives the string without the prompt. |
| `graft migrate [--apply]` | Run your own [migrations](/docs/migrations). Lists them only, until `--apply`. |
| `graft harden <role>` | Give an existing database role the limited rights a deployed app needs. See [Hardening](/docs/hardening). |
| `graft content` | List documents in the compiled index |
| `graft pull [doc...]` | Write what is published into your files, in a database-sourced project. Keeps files you changed. `--force` takes the published version over a conflict. |
| `graft push [doc...]` | Publish the files you changed since your last pull, checked as a compile would. Refused if someone published them since. `--dry-run`, `--force`. |
| `graft mirror` | Commit what was published since the last run to the repository in `GRAFT_GITHUB_REPO` |
| `graft check` | Check every content file: schema, slugs, MDX safety, references. Needs no database. Exits 1 on a problem. |
| `graft ci changes` | Print `content-only=true` when only content changed, and write it to `$GITHUB_OUTPUT`. `--base <ref>` |
| `graft ci skip-build` | Exit 0 when a deploy can be skipped: only content changed and it is already live from the database |
| `graft ci init` | Write a workflow that runs `graft check` on content changes |
| `graft content import [--dry-run]` | Load the files under `contentDir` into the database, for a project with `content = { source: "database" }`. Every file is checked first. Only documents with nothing published come in: a published document is never overwritten, and a deleted file deletes nothing. Safe to run again. |
| `graft compilations` | List recent compiles and what each one changed |

## Approve actions

| Command | What it does |
| --- | --- |
| `graft approvals` | List actions waiting for approval |
| `graft approve <id>` | Approve one. The caller then repeats its call with the id. |
| `graft deny <id>` | Deny one |

## Work with preview branches

| Command | What it does |
| --- | --- |
| `graft branch` | List branches |
| `graft branch create <name>` | Create a preview branch. `--from <parent>` (default `main`), `--backend neon` for a Neon fork. |
| `graft branch drop <name>` | Delete a branch |
| `graft merge <name> [--apply]` | Merge a branch into `--into` (default `main`). Reports only, until `--apply`. |

## Flags

| Flag | Works with | Meaning |
| --- | --- | --- |
| `--branch <name>` | compile, dev, migrate, mcp, serve, studio, content, compilations | Work on a preview branch instead of `main` |
| `--apply` | migrate, merge | Make the change. Without it, these only report. |
| `--prune-unknown` | compile | Remove index entries for collections the schema no longer has. Use after renaming or deleting a collection. |
| `--json` | compile | Print the branch, commit, and change list as JSON on stdout. See [Print what a compile changed](#print-what-a-compile-changed). |
| `--dry-run` | add, content import, push | Preview what would change without writing it |
| `--force` | pull, push | Settle conflicts: pull takes the published version, push publishes yours |
| `--base <ref>` | ci changes, ci skip-build | The ref to compare against. Default: the pull request's base branch, the host's previous deploy where the host names it, or the commit a push started from, else the previous commit. `skip-build` never skips on the previous commit alone |
| `--overwrite` | add, asset put | Replace files that differ (add), or the file already stored under the key (asset put) |
| `--port` / `--host` | serve, studio | Where to listen. Defaults to this machine only. |
| `--studio` | serve | Include Studio. `GRAFT_STUDIO=1` does the same. |

## Update notice

When a newer Graft is on npm, `graft` prints a notice on stderr after the
command finishes. `graft dev`, `graft serve` and `graft studio` print it while
they run. It names the new version, the version you have, and the
[upgrade guide](/docs/upgrading). On a beta, the notice is yellow, because beta
releases often include security fixes. On a stable release it is cyan.

The CLI asks the registry at most once a day and caches the answer in
`~/.cache/graft/update-check.json` (or under `XDG_CACHE_HOME`). It uses the
registry in `npm_config_registry` when you set one. A slow or unreachable
registry never fails or delays a command by more than 1.5 seconds.

The check is off when `GRAFT_NO_UPDATE_CHECK=1` or `CI` is set, and for
`graft mcp`, `--help` and `--version`. Set `NO_COLOR` to print it without
color.

## Which commands need a database

Graft reads `.env` from the current folder or any folder above it.

- **Static engine:** `graft compile`, `graft dev`, and `graft mcp` need no
  database. The index is written to `.graft/index.db`.
- **Postgres engine:** when `graft.config.ts` sets `index = "postgres"`,
  every command that reads or writes the index needs `DATABASE_URL`, including
  `graft compile`, `graft dev`, and `graft mcp`. `graft init`, `graft add`,
  and `graft asset put` never need it.
- **On either engine,** these always need `DATABASE_URL`: `graft db migrate`,
  `graft branch`, `graft merge`, `graft serve`, `graft studio`,
  `graft content`, `graft compilations`, `graft approvals`, `graft approve`,
  `graft deny`, and `graft harden`. `graft migrate` needs it once the project
  has migrations.

Studio uses the same operations as the CLI and MCP. See
[Studio](/docs/studio#do-it-without-studio) for the mapping.
