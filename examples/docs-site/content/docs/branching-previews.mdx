A branch gives an isolated view of content for previews. Two backends share the
same commands:

| Backend | How | Cost | Where |
| --- | --- | --- | --- |
| `overlay` (default) | `branch_id` rows over `main`; branch wins; tombstones hide | Instant; copies nothing | Any Postgres |
| `neon` | Physical copy-on-write database fork | Instant (Neon CoW) | Neon |

```sh
graft branch create preview-pricing
graft branch create big-redesign --backend neon
graft branch list
graft compile --branch preview-pricing
graft branch drop preview-pricing
```

Reads are branch-aware. Pass `branch` to the SDK client. Overlay chains inherit
parent documents; the leaf wins. Soft-deleted (tombstoned) parent rows stay hidden.

## Data inheritance

Previews inherit **content**, never operational data. A Neon fork starts with
cleared `data_records` and approvals. You preview the site shape, not a copy of
production users.

## Merge

```sh
graft merge preview-pricing            # dry-run report
graft merge preview-pricing --apply    # replay ledger → move data rows → recompile
```

Content merge stays git-authoritative. Merge the git branch first so content
migration files exist. `graft merge` never touches git. It:

1. Replays the `migrations_applied` ledger onto the target
2. Moves (or copies, for Neon) `data_records` created on the branch
3. Recompiles the working tree into the target

Default is dry-run. Pass `--apply` to execute (same consent model as
`graft migrate`).

## Cache invalidation

Every projection returns a ChangeSet. SDKs map it to tags:

- `tagsFor(...)` on reads
- `tagsForChanges(branch, changeSet)` after compile

A preview branch never invalidates main's tags. See
[Reading content](/docs/reading-content).
