<p className="kicker">Give writers a visual editor, without giving up Git.</p>

<TierBadge tier="postgres" />

Not everyone on your team wants to edit Markdown files and run Git commands.
Studio is a web UI for them: they browse the content, edit a document in a
rich editor, review what they changed, and commit it. Everything still ends up
as files in Git, exactly as if a developer had edited them.

Studio is optional. Every action in it also exists in the CLI and over MCP, so
nothing is locked inside the UI. It needs the [Postgres engine](/docs/tiers),
because it compares your files with the compiled index.

## Open Studio

```sh
graft studio
```

This starts Studio on your machine, at port 4983, and opens your browser. Only
your machine can reach it.

To serve it from a deployment instead, mount it in the Graft server:

```sh
graft serve --studio    # served at /studio
```

Setting `GRAFT_STUDIO=1` does the same without the flag. Either command accepts
`--branch <name>` to edit a [preview branch](/docs/branching-previews) instead
of `main`. The UI then stays on that branch, so it can never show `main` while
the server is serving a preview.

## Find your way around

| View | Use it to |
| --- | --- |
| Overview | See document counts, what changed recently, and anything out of date |
| Collections | Browse the content and open a document to edit |
| Schema | Look up every collection's fields (read-only) |
| Approvals | Approve or deny actions waiting for a person |
| Branches | See preview branches |
| History | See past compiles, and roll back to one |
| Settings | Appearance, project details, and package versions |

Each view has its own URL, so you can bookmark or share a link to it.

## Why a document is marked "drifted"

Your files are the source of truth, and the index is a compiled copy of them.
After you edit a file, and before you compile, the two disagree. Studio shows
that instead of hiding it. Each document is in one of four states:

| State | Meaning | What to do |
| --- | --- | --- |
| `synced` | The file and the index match | Nothing |
| `drifted` | The file was edited since the last compile | Compile |
| `unindexed` | The file exists but has never been compiled | Compile |
| `orphaned` | The index still has it, but the file is gone | Compile, which removes it |

The header counts every document that is not `synced`, and has a button to
compile.

If one collection's files cannot be read, that collection shows its error and
the rest of the tree still works. Operational data collections are marked as
such, because their records live in Postgres and are only changed through
[functions](/docs/functions-and-access).

## Edit a document

A document opens in one of two editors:

- **Rich** works like a word processor, and saves back to Markdown.
- **Raw MDX** shows the source text.

Rich is only offered when it can save the document without changing anything
you did not touch. When a document opens, Studio converts it with the rich
editor and compares the result with the original file. If the content would
change, beyond harmless formatting such as list markers or table spacing, the
document opens in Raw and Rich is disabled. This matters for MDX: a change as
small as escaping `{` can break a page that looks identical.

### Saving

Studio saves automatically, and it never rewrites a file you only opened:

- It ignores changes until you actually type or click in the editor.
- It refuses to save a file whose contents would be identical to what it
  loaded.

A save is checked exactly like a CLI or agent edit. Studio validates the
frontmatter against the schema, runs the [MDX safety](/docs/mdx-safety) check,
writes the file, and recompiles. A document that fails gets the same
`SCHEMA_VALIDATION_FAILED` error, with a message saying which field to fix.

## Review and commit your changes

The **Changes** drawer shows what you have changed since the last Git commit,
read straight from Git:

- Each changed file is listed with what happened to it: added, modified,
  deleted, or renamed.
- Click a file to see its diff. Images and other binary files have no diff.

Select the files to include, write a message, and commit. Studio commits only
files it showed you, checks your Git identity before changing anything, and
leaves any other work you had staged untouched.

If the project is not a Git repository, the drawer says so. Content still
compiles and serves without Git.

## Revert from a compilation

Every compile records the Git commit it read. So in History you can pick a past
compile and restore your content to exactly how it was then. Studio restores
the files and recompiles.

It only offers this when it is safe. It first checks that the commit exists in
this copy of the repository and that you have no uncommitted content changes
the revert would overwrite. The restored files are staged, not committed, so you
review and commit the revert yourself.

## Give people access

Studio's actions are split into three permissions, so you can let someone, or
an agent, read without letting them change content or approve actions:

| Scope | Allows |
| --- | --- |
| `studio:read` | Browsing content, the schema, branches, history, diffs, and pending approvals |
| `studio:write` | Saving, compiling, committing, and reverting |
| `approvals:decide` | Approving and denying |

`graft studio` on your own machine asks for no login, because only you can
reach it. When Studio is reachable from other machines, it requires a token,
and it warns at startup if you have not set `GRAFT_DEV_TOKEN`.

Studio records every approval decision against a verified identity, never a
name the request supplies. Otherwise someone could approve their own request.
On a [hardened](/docs/hardening) deployment, approvals can only be decided with
the operator login, so the Approvals view there is read-only.

## Do it without Studio

| In Studio | From the CLI | Over MCP |
| --- | --- | --- |
| Browse content | `graft content` | `list_content` |
| Save a document | Edit the file, then `graft compile` | `write_content` |
| See past compiles | `graft compilations` | `list_compilations` |
| See branches | `graft branch list` | `list_branches` |
| See pending approvals | `graft approvals` | `list_approvals` |
| Approve or deny | `graft approve` / `graft deny` | `decide_approval` |

The UI itself uses the [Studio API](/docs/studio-api), which you can call
directly.
