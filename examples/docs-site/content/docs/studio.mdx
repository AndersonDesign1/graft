<p className="kicker">Give writers and merchandisers an editor, without giving up Git.</p>

<TierBadge tier="postgres" />

Not everyone on your team wants to edit Markdown files and run Git commands.
Studio is an editor for them. They find an entry, change it in a form built from
your schema, and publish. Everything still ends up as files in Git, exactly as
if a developer had edited them, and nothing an editor can do in Studio is
unavailable to an agent or a developer.

Studio needs the [Postgres engine](/docs/tiers) for its developer views
(history, approvals, branches). Content stays files in Git either way.

## Open Studio

```sh
graft studio
```

This starts Studio on your machine, at port 4983, and opens your browser. Only
your machine can reach it, and saves go to the files in your checkout.

To give a team a Studio URL, with sign-in and saves that land on GitHub, see
[Host Studio for your team](/docs/studio-hosting).

## Find your way around

Content comes first.

| Where | What it is for |
| --- | --- |
| Home | What is waiting to publish, and every collection with its count |
| A collection | A table of its entries: search, filter, sort, select many |
| An entry | Its fields and its content, saved as you type |
| Publish | Every unpublished change, what changed in it, and the button that puts it live |
| Developer | Index health, schema, history, branches, approvals and settings |

Press <kbd>⌘K</kbd> anywhere to find an entry by name, create one, or jump to a
collection. Search runs on the server, so it is as quick on five thousand
products as on fifty.

## Find content

A collection opens as a table. The columns are the first few short fields of
its schema, so a product list shows price, status and category without any
configuration.

- **Search** matches names, URL names and text fields.
- **Filter** by status (all, unpublished, published) and by any choice,
  yes/no or reference field.
- **Sort** by name, last edited or any column.
- **Select** several entries to publish, discard or delete them together.

The table loads a page at a time as you scroll.

## Edit an entry

An entry opens as a page: its title at the top, its fields below, and its
content last.

Fields are built from your schema. Each has its label, says if it is optional,
and shows its help text. Money is typed as money, choices are buttons or a
list, references open a search over the other collection, lists of images are a
gallery, and repeated groups such as product variants fold into one line each.
See [Schema](/docs/schema) for how to declare them.

Problems are shown on the field, in words, before anything is saved: "Keep the
summary to 240 characters", "Price can't be less than $0.00". Studio does not
save an entry until it is valid, which is the same rule every agent write
follows.

The content is edited in a rich editor that saves back to Markdown. Studio only
offers it when it can save the content without changing anything you did not
touch. When it can't, the content opens as Markdown beside the same form. This
matters for MDX: a change as small as escaping `{` can break a page that looks
identical. Use **Edit source** in the entry's menu to edit the whole file.

### Saving

Studio saves automatically, and never rewrites an entry you only opened. Every
save carries the version you started from. If the entry changed somewhere else
in the meantime (another tab, a teammate, an agent), Studio does not overwrite
it. It shows you, and you choose to load the newer version or keep yours.

## Publish

Saved changes are drafts until you publish them. The Publish button in the top
bar shows how many are waiting, and opens a sheet that lists them as entries
("Wool Hat, Edited") with the fields that changed ("Price: $25.00 → $29.00").
Choose what to include and press the button. What it does depends on where
Studio runs:

| Studio | Publish button | What happens |
| --- | --- | --- |
| On your machine | Commit | A Git commit of the selected files. Nothing is pushed |
| Hosted, editor | Publish | One commit on your production branch; the site redeploys. With `GRAFT_STUDIO_PUBLISH=pull-request`, a pull request instead |
| Hosted, contributor | Submit for review | A pull request for someone to merge |

**Discard** throws a draft away and leaves the published version as it is.
Deleting an entry is a draft too: it stays live until you publish the deletion,
and the toast that follows a delete has an Undo.

## Give people access

On your own machine Studio asks for no login. A hosted Studio has sign-in, with
GitHub or an invite link, and four roles: viewer, contributor, editor and
admin. See [Host Studio for your team](/docs/studio-hosting#roles).

The roles name scopes, which is also what bearer tokens carry:

| Scope | Allows |
| --- | --- |
| `studio:read` | Browsing content, the schema, history and pending approvals |
| `studio:write` | Saving drafts, discarding, compiling. Publishing opens a pull request |
| `studio:publish` | Publishing straight to the production branch |
| `approvals:decide` | Approving and denying |

## Developer views

Under **Developer**: index health (each document's state against the compiled
index), the schema, the compile history with restore, branches, approvals, and
settings. The index states are explained in [How Graft works](/docs/the-model).

## Do it without Studio

| In Studio | From the CLI or Git | Over MCP |
| --- | --- | --- |
| Find content | `graft content` | `list_content`, `search_content` |
| Save an entry | Edit the file, then `graft compile` | `write_content` |
| Delete an entry | Delete the file | `delete_content` |
| Publish, locally | `git commit` | |
| Publish, hosted | Merge the draft branch (all of its changes at once) | `publish_drafts` |
| Discard a draft | `git restore` | `discard_drafts` |
| See past compiles | `graft compilations` | `list_compilations` |
| Approve or deny | `graft approve` / `graft deny` | `decide_approval` |

The UI itself uses the [Studio API](/docs/studio-api), which you can call
directly.
